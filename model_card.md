### Case study: "Where is the auth token generated?"

**Ground truth (AUTH.md, "Token Generation"):** "Tokens are created by the
`generate_access_token` function in the `auth_utils.py` module. The function
takes a user ID and returns a signed JSON Web Token string."

**Outputs**

- **Mode 1 (Naive LLM):** Said it needed "a little more context about your
  codebase", then listed places tokens are *typically* generated: an
  `auth.controller.js` or `auth.py` file, a provider like Auth0 or Firebase,
  or a helper like `generateToken()`. On another run it only asked for
  context: "It looks like you didn't include the codebase..."
- **Mode 2 (Retrieval only):** Returned three AUTH.md sections, in this order:
  "Token Generation", "Environment Variables", "Authentication Guide" (the
  intro). The answer is in the first section.
- **Mode 3 (RAG):** "the auth token is generated by the `generate_access_token`
  function located in the `auth_utils.py` module. I relied on: `AUTH.md`"

**1. Most grounded:** Mode 2 is the most strictly grounded, because it shows
only verbatim documentation and cannot add anything. Mode 3 is grounded too:
every claim in its answer appears word for word in the retrieved
"Token Generation" section, and it names its source file. Mode 1 is not
grounded at all.

**2. Easiest to understand:** Mode 3. It answers in one sentence with the
exact file and function. Mode 2 puts the right section first, but the reader
still has to scan about 30 lines across three sections, and the last two do
not answer the question. Mode 1 is long and never gives the answer.

**3. Unsupported information:** Mode 1. None of the file names or functions
it suggested (`auth.controller.js`, `generateToken()`, Auth0, `jsonwebtoken`)
appear in our docs. It did hedge ("in most modern applications"), so this was
generic guessing rather than a confident false claim, but a developer could
still waste time searching for files that do not exist. Its wording also
changed between runs, which shows its output is not tied to any fixed
source. Modes 2 and 3 contained no unsupported claims in this test.

**4. Evidence used:**

| Mode | Evidence available | Evidence used |
|------|--------------------|---------------|
| 1. Naive LLM | None: in our implementation the prompt contains only the question, not the docs | None. Fell back on general knowledge about other projects. |
| 2. Retrieval only | Top 3 sections by score | All three shown as-is, best match first. No judgment about which one answers the question. |
| 3. RAG | The same 3 sections as Mode 2 | Used the relevant section ("Token Generation"), ignored the other two, and cited the file. |

**5. What could still go wrong in RAG:**

- **Retrieval only matches words, not meaning.** "Token Generation" now
  ranks first with a score of 4, well ahead of the next section (2), because
  stemming lets "generated" match "Generation" and the heading bonus rewards
  sections whose heading matches the question. But a question worded with
  different vocabulary (for example "Where are JWTs created?") would not
  benefit from either fix.
- **Citations are not verified.** "I relied on AUTH.md" is written by the
  model; no code checks that the cited file supports the claim.
- **The prompt rules are instructions, not guarantees.** Gemini could add
  outside knowledge (for example, a signing algorithm, which the docs never
  name) and still sound grounded.
- **RAG repeats the docs as written.** If `auth_utils.py` were renamed and
  the docs not updated, RAG would confidently give the outdated answer.

**Takeaway:** RAG produced the best answer by combining Mode 2's evidence
with Mode 1's readability. Its correctness depends on retrieval putting the
right section in front of the model.

### Observations

#### 1. Overview of the three modes

- **Naive LLM (Mode 1)** sends only the question to Gemini. The model never
  sees our documentation, so it answers from general knowledge about other
  projects.
- **Retrieval only (Mode 2)** splits the docs into heading-based sections and
  scores each one by how many meaningful question words it contains. Common
  words like "the" are ignored, word endings are trimmed so that "connect"
  matches "connection", and words that also appear in a section's heading
  count double. It shows the top 3 sections exactly as written, or refuses if
  no section scores at least 2. No LLM is involved.
- **RAG (Mode 3)** runs the same retrieval as Mode 2, then gives those
  sections to Gemini with instructions to answer only from them, cite the
  file, and say "I do not know based on the docs I have" if they are not
  enough.

#### 2. Naive LLM: confident but weakly grounded

The clearest example was **"Which fields are stored in the users table?"**
Mode 1 answered: "Based on the standard schema documentation, the `users`
table typically stores..." and listed `id`, `username`, `email`,
`password_hash`, `created_at`, and `updated_at`.

The actual table in DATABASE.md has `user_id`, `email`, `password_hash`, and
`joined_at`. Only two of the six fields were right, and two of the four real
columns were missing or renamed. What makes this answer dangerous is the
phrase "based on the standard schema documentation". It sounds like the model
read documentation, but it never saw any.

Other Mode 1 answers followed the same pattern:

- **"Which endpoint lists all users?"** It answered `GET /users` with no
  hedging. The real endpoint is `GET /api/users`.
- **"How does a client refresh an access token?"** It described a full OAuth
  flow (`POST /oauth/token` with `grant_type=refresh_token` and a
  `client_id`). Our docs describe a different design: call `/api/refresh`
  with the current token in the Authorization header.

These answers were well formatted and sounded authoritative, which makes them
easy to over-trust.

#### 3. Retrieval only: accurate but hard to read

For **"Where is the auth token generated?"**, Mode 2 returned three AUTH.md
sections: "Token Generation", "Environment Variables", and the
"Authentication Guide" intro. Everything shown was real documentation, so
nothing was made up, and the right section came first. But the output is
about 30 lines long, and two of the three sections do not answer the
question. A reader still has to read the evidence and decide for themselves
what the answer is. Retrieval is trustworthy but does not answer: it hands
you evidence and leaves the work to you.

#### 4. RAG: clearer and evidence-based

For the same question, RAG answered in one sentence: "the auth token is
generated by the `generate_access_token` function located in the
`auth_utils.py` module", and named AUTH.md as its source.

RAG also corrected every naive mistake from point 2:

- **Users table:** it listed `user_id`, `email`, `password_hash`, and
  `joined_at`, matching DATABASE.md exactly.
- **Users endpoint:** it answered `GET /api/users`.
- **Token refresh:** it answered "by calling `/api/refresh`" from AUTH.md.
- **Database connection:** it explained `DATABASE_URL` with the SQLite and
  PostgreSQL formats from DATABASE.md.

All 8 sample questions in `dataset.py` got a correct RAG result: 7 correct,
cited answers and a correct refusal for "Is there any mention of payment
processing in these docs?".

#### 5. RAG failing

For **"How do I log in?"**, DocuBot replied "I do not know based on these
docs." The docs *do* answer this: API_REFERENCE.md documents
`POST /api/login`, and AUTH.md's "Client Workflow" says to "Send credentials
to `/api/login`".

The cause was retrieval. After removing stop words, the only meaningful word
left is "log". Our matching compares whole words, so "log" does not match
"login" or "/api/login". The best section scored only 1 point, below the
refusal threshold of 2, so DocuBot refused before Gemini was ever called.
This is a safe failure (no hallucination), but it is still a failure: the
answer exists in the docs.

A smaller weakness: for "How does a client refresh an access token?", RAG's
answer was correct but brief. The most detailed section, "POST /api/refresh"
in API_REFERENCE.md, did not make the top 3, so the answer left out details
like sending the current token in the Authorization header.

#### 6. Lessons learned

- **Retrieval is the weakest link in RAG.** When retrieval found the right
  section, RAG answered correctly. When it missed ("How do I log in?"), RAG
  could not recover. The LLM can only be as good as the evidence it is
  given.
- **Grounding matters more than fluency.** Naive answers were often the
  longest and most polished, and also the least accurate. Sounding confident
  is not evidence of being right.
- **Hallucinations come from missing evidence.** Mode 1 had no docs, so it
  filled the gaps with typical answers from other projects (`/users`,
  `created_at`, OAuth). Giving the model the right section and telling it to
  stay inside it removed those errors in our tests.
- **Refusing is better than guessing, but not all refusals are correct.**
  The refusal on payment processing was right; the refusal on "How do I log
  in?" was wrong. A refusal needs to be checked against the docs just like
  an answer.
- **Small, explainable fixes made a big difference.** Before stemming and the
  heading bonus, "How do I connect to the database?" was wrongly refused, and
  "Token Generation" only reached the top 3 through tie-breaking. After them,
  a section that answers the question ranked first for every sample question
  we checked, and
  the evaluation hit rate went from 0.75 to 1.00.
- **Our results are optimistic.** We chose the refusal threshold and the
  extra stop words while testing on the same 8 sample questions we evaluate
  on. New questions, especially ones that use synonyms, will not all work
  this well.
